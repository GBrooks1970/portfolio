Maintaining this document: maintenance guide.

Five ordered routes through the portfolio. The Tool Atlas answers 'what is this tool and where is it used?' one tool at a time; these paths teach one idea at a time across several projects, so a reader does not have to guess which repository to open first.

Status. First edition, 6 October 2026. 25 of the 26 stages were run. 21 passed as written (stage 1.3 with a setup deviation, and five stages on a scratch Node 24 install; stages 1.5 and 5.5 with commands taken from the project's own documentation, because the outline named none). Stage 2.4 passed after a dotnet restore that its command assumes (finding 10). Stage 2.5 passed with two deviations (port 8001, and the gate run in a Linux container on normalised reports; finding 8). Stage 4.3 ran and reported real image-pin drift, as it is designed to; the pin has since been refreshed (finding 11). Stage 4.4 failed to start on Windows on 6 October and passed on 7 October after the probe was fixed (finding 7). 1 stage was not run (4.2), because its Docker stack was in use by another session. It is labelled in place. Stages 5.3 and 5.4 failed in the cloud container on a browser-build mismatch and passed as written on a machine with the matching browsers.

1. How to use this

Read the paths in order 1 to 4; path 5 can be read alone. Every stage has the same parts.

Part What it holds
Tool and where The Atlas entry, and the project and folder to open.
Read The decision record that explains the choice.
Do One command (or two), copied from the project's package.json or README.
Captured result What the command printed when run, with the duration. Not run: says so.
Watch for The common mistake. Drawn from a decision record or from the captured run.

Reading a Captured result is not the same as running the command. Counts will change as projects move; the durations are from one machine (section 2) and show scale, not a benchmark.

Projects still in progress. Two projects in these paths are not finished, and the stages that use them say so. saleor-graphql-automation (stages 3.4 and 4.2) is active: Phases 0 and 1 are done and Phase 2 is underway. tradeblotter-wpf-screenplay (stages 1.5 and 5.5) has TB-01 to TB-08A complete; TB-08B is blocked on a Ranorex licence and the project is parked.

8. What the run found

These are findings about the portfolio, kept here because they change what a reader will experience.

  1. The outline omitted a setup step. Stage 2.3 needs pip install -c requirements-test.lock -e ".[test]"; stage 3.5 needs pip install gherkin-official==42.0.1. Both are in the projects' READMEs. Corrected above.
  2. The parity gate cannot give a partial pass. Stage 2.5 shows this directly. It is a property to teach, not a defect.
  3. Two exact commands fail on a machine whose Playwright browsers do not match the pinned version (5.3, 5.4). The projects pin Playwright 1.61.1, which wants Chromium build 1228. On a Windows machine whose Playwright browsers matched, both exact commands passed as written on 6 October 2026 (5.3: 16 tests; 5.4: 31 tests, including the WebKit project), with no npx playwright install. The failure is the browser mismatch, not the commands.
  4. A Cypress binary download can arrive truncated through a proxy (1.3). It does not affect the unit tests.
  5. Node 24 is required by three projects (orangehrm, sudoku demoapp001, and loan-origination, which also accepts Node 22.22.3 or later). The authoring environment's 22.22.0 does not satisfy any of them.
  6. The mutation score on the day was 69.12%, not the baseline's 69.57%, and the project already explains why. Its docs/mutation-testing.md records that the first CI run scored 69.12% against the same commit: 620 mutants killed either way, with the 4 that timed out locally surviving on a faster machine. This run matches that CI figure (620 killed, 0 timeouts, 239 survived). The baseline needs no correction. An earlier version of this section said the backlog figure was wrong; that was my misreading.
  7. The repeatability probe could not start on Windows, and has been fixed (4.4). scripts/run-repeatability-probe.mjs called spawnSync('npm.cmd', …) without a shell, and Node 24.18.0 failed with EINVAL in 6 s. The Linux CI job could never show it. The fix (juice-shop DAST-M5, PR #12, ba76110) starts npm through process.execPath and npm_execpath, with a shell fallback on Windows and plain npm elsewhere. npm_execpath exists only under an npm-launched process, so the fallback is needed for a direct node run. A real-spawn unit test catches the original defect: against the old behaviour it fails with the same EINVAL. The probe then passed on Windows (496 s) and on Linux CI (4 min 23 s). A sweep of every child_process call in the portfolio found one more Windows-only break of the same kind, loan-origination tools/build-reports.mjs (spawnSync('npx') without a shell), recorded in that project's backlog Risk #3.
  8. The parity gate does not run on Windows (2.5). tools/check-parity.mjs fails twice. Line 9 builds the repository root from new URL('..', import.meta.url).pathname, which gives /D:/… and then D:\D:\… (ENOENT … scandir). Past that, Cucumber on Windows records feature URIs with backslashes (..\..\features-shared\domain-rules\…), and line 55 splits them on features-shared/, so it throws Cannot read properties of undefined (reading 'split'). The reports and the verdict are sound once the separators are normalised; the gate script is what needs a fix. CI runs on Linux, which is why it passes there.
  9. Port 8000 is not free on a machine running other Docker work. The Node service in test:api, test:angular and test:nextjs defaults to port 8000. Another container held it here and answered /health with 404, so each suite stopped with did not become healthy. PORT (api) and API_PORT (UI suites) override it.
  10. dotnet test --no-restore assumes a restore that a fresh checkout does not have (2.4). On a machine that had not restored the solution at the SDK in use, it exited 1 with NETSDK1005 … doesn't have a target for 'net10.0'. Run dotnet restore first; the tests then pass (83 in all).
  11. The ParaBank build pin was stale on 6 October and has since been refreshed (4.3). MavenBuilder (maven:3.9.16-eclipse-temurin-17-noble) resolved to a different digest from the one recorded in config/container-image-pins.psd1, while ParaBankRuntime still matched. This is the validator doing its job: DR-PB-11 treats it as a reviewed refresh, not a build failure, and the 4.3 run changed nothing. The refresh followed the policy as PB-PIN-06 (plan, six-platform provenance review, full five-command contract, owner merge): parabank PR #49, merge 25c83b8, digest sha256:880934ae…126737bf to sha256:1a352420…ed698584, version and source revision unchanged. Temurin base contents and CVEs were not reviewed. The upstream index can move again, and the weekly pin-drift lane will say so.
  12. pwsh -File does not split a comma list into an array (5.5). pwsh -NoProfile -File ./scripts/run-benchmarks.ps1 -Drivers flaui,ranorex-mock,ranorex failed in 3 s: Cannot validate argument on parameter 'Drivers'. The argument "flaui,ranorex-mock,ranorex" does not belong to the set …. Run it from a PowerShell prompt, or with pwsh -Command "./scripts/run-benchmarks.ps1 -Drivers flaui,ranorex-mock,ranorex -AllowUnavailable", as docs/benchmark-harness.md shows. The script is not at fault.
