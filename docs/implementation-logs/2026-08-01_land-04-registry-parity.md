## Decisions

- Rebuild from `data/registry-lock.json`'s full source commit, not a mutable branch tip. This makes
  every PR reproducible and ensures a lock cannot claim provenance it does not match.
- Check out the canonical repository with full history in CI instead of fetching YAML in visitors'
  browsers or using a runtime API. The deployed page remains dependency-free and offline-static.
- Use the ordinary `pull_request` event with `contents: read`, no secrets and no persisted
  credentials. Proposed code never runs in a privileged `pull_request_target` context.
- Pin `actions/checkout` v7.0.1 and `actions/setup-python` v7.0.0 to reviewed full SHAs; both use the
  Node 24 action runtime and avoid the deprecation warning observed in GitHub's generated Pages job.
- Validate the existing `data-showcase-count` marker and actual role-specific DOM inventory rather
  than trusting prose or file-byte equality alone.

These choices implement the source boundary already accepted in
`docs/decisions/001-presentation-ownership.md`; no new ADR was required.

## Failures and recovery

The first clean Windows-worktree run failed both generator `--check` and the byte-stability unit
test because Git had converted `index.html` from generated LF bytes to CRLF. This was a repository
checkout contract defect, not content drift. Adding `.gitattributes` with
`index.html text eol=lf` and regenerating through `tools/generate_site.py` restored exact bytes; the
parity command, generator check and all 10 tests then passed locally and in Linux CI.

## Durable lessons

- A byte-stable generator needs an explicit Git end-of-line contract; writing LF is insufficient if
  checkout filters can replace it later.
- A provenance lock is trustworthy only when CI can independently reproduce it from the recorded
  immutable source.
- Generated-output equality and semantic inventory checks complement each other: bytes catch stale
  output, while role/count checks express the public contract and produce actionable failures.
- Cross-repository PR checks can remain safe for forked contributions when the upstream source is
  public and the workflow is strictly read-only and secret-free.
